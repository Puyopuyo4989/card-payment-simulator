## R2. 【決めてほしい】表の作り：申込と変更履歴を分けるか

spec の Key Entities は「申込」と「状態の変更履歴（1件の申込に0〜2行）」。

### 案A：2つの表に分ける（推奨）

- `card_application`（申込）：申込番号・6項目・**今の状態**・申込日時・更新日時・version。
- `card_application_status_history`（変更履歴）：申込番号（外部キー）・変更日時・変更前の状態・変更後の状態・担当者名・否決の理由。
  1回の状態の変更で1行足す。**足すだけで、直さない・消さない**。
- **理由**:
  - spec の言葉（申込・変更履歴）と表が1対1になり、説明しやすい。
  - 一覧の絞り込み（FR-008）は `card_application.status` だけで済み、結合がいらない。
  - 「否決の理由は否決のときだけ」を、履歴の行の制約（`to_status = 'REJECTED'` のときだけ理由がある）として DB で守れる。
  - 状態の変更は「申込の更新1つ＋履歴の追加1つ」を1つのトランザクションで行うだけ。
  - 次のスプリントで、担当者名をログイン中のユーザーに置き換える（ADR 0010）ときも、履歴の表の列を変えるだけで済む。
- **弱いところ**: 表が2つになり、詳細の取得で2回（または結合で1回）読む。100件規模では問題にならない。

### 案B：1つの表にまとめる

- 申込の表に「審査中にした日時・担当者名」「承認／否決にした日時・担当者名・理由」の列を持つ（変更は最大2回なので、列で足りる）。
- **採らない理由**: 結合はいらないが、画面の「変更履歴」を列から組み立て直すことになり、spec の「履歴に1行が加わる」と形が違う。
  否決のときだけ理由がある、審査中のときは承認の列が空、などの組み合わせのルールが増える。状態の種類が増えると表を変える必要がある。

### 案C：履歴だけを持ち、今の状態は履歴から求める

- **採らない理由**: 一覧の絞り込みのたびに「最新の履歴」を求める集計がいる。楽観ロックをかける行もはっきりしない。この規模には重い。

## R3. 【決めてほしい】状態の遷移のルール（申込 → 審査中 → 承認／否決）をどこに書くか

### 案A：ドメイン（Spring に依存しない Java）に書き、DB は値の制約だけで守る（推奨）

- `ApplicationStatus`（enum）が「次に進める状態」を持つ（`APPLIED → UNDER_REVIEW`、`UNDER_REVIEW → APPROVED / REJECTED`、
  `APPROVED`・`REJECTED` は次がない）。
- `CardApplication.changeStatus(…)`（ドメインのオブジェクト）が、遷移のルール・否決の理由の要否を確かめ、
  許されないときは理由つきのドメインの例外（`StatusTransitionException`。理由：`REVIEW_REQUIRED_FIRST`・`ALREADY_DECIDED`・`NOT_ALLOWED`）を投げる。
  リボ払いの `RevolvingNotPayableException` と同じ形で、Web 層が理由をメッセージに変える（002 の R4）。
- サービス（`CardApplicationService`）は、読む → ドメインに確かめさせる → 保存する、の順に呼ぶだけ。ルールの if 文を持たない。
- DB は **値の制約**（状態は4つのどれか、否決の行だけ理由がある、年収の範囲など）だけを `CHECK` で持つ。
  遷移（どこからどこへ）は DB に書かない。
- **理由**:
  - TDD（原則I）：遷移の 4×4＝16 通りを、DB も Spring もなしの単体テストで、すぐに全部確かめられる（SC-004「100%行われない」の根拠になる）。
  - 計算をドメインに置いた分割払い・リボ払いと同じ形で、説明が1つで済む。
  - DB の `CHECK` は、コードの誤りで変な値が入るのを止める最後の守りになる（多層防御。ADR 0008 の考え方）。

### 案B：サービスの if 文に書く

- **採らない理由**: 動きは同じだが、ルールのテストにサービス（リポジトリの差し替え）が要る。ルールがサービスの中に散らばりやすい。

### 案C：DB（トリガー）に書く

- **採らない理由**: どのコードからでも守れるが、テストに DB が要り、画面に出すメッセージ（どう直せばよいか）を作りにくい。
  ルールが Java と SQL に分かれ、レビューしにくい。

## R4. 【決めてほしい】楽観ロックのやり方と、ぶつかったときの API の応答（FR-019）

### やり方

#### 案A：申込の表に `version`（整数）の列を持つ（推奨）

- 詳細の API が `version` を返す。画面は、状態を変えるときに、表示していた `version` をそのまま送る。
- 保存は `UPDATE card_application SET status = ?, updated_at = ?, version = version + 1 WHERE application_number = ? AND version = ?`。
  **更新された行が0行なら、ぶつかった**とみなし、履歴は足さずにトランザクションを戻す。
- 先に読んだ時点で `version` が違えば、その場で「ぶつかった」とする。読んでから `UPDATE` までの間に変わった場合は、
  上の `WHERE version = ?` が止める。PostgreSQL（READ COMMITTED）では、同じ行への2つの `UPDATE` は順に実行され、
  あとの方は先の方のコミット後の行で `WHERE` を確かめ直すので、**2人とも成功することはない**。
- **理由**: 楽観ロックとして一般的で、説明しやすい。状態以外の更新ができる機能が将来足されても、そのまま使える。
  JPA の `@Version` と同じ考え方を、`JdbcClient` の1文で書ける。

#### 案B：`version` の列を持たず、「変更前の状態」を条件にする

- 画面が「今は審査中のはず」（`fromStatus`）を送り、`UPDATE … WHERE status = ?` にする。
  この機能では状態が戻らない（前に進むだけ）ので、状態そのものが version の代わりになる。
- **採らない理由**: 列が1つ減るが、「状態が戻らない」という今のルールに頼った作りになる。差し戻しなどを足すと成り立たない。
  依頼にあった「version の列」の方が、説明のときに一般的なやり方として示せる。

#### 案C：HTTP の `ETag` / `If-Match` ヘッダーで version を送る

- **採らない理由**: HTTP の作法としてはきれいだが、ぶつかったときは本来 `412 Precondition Failed` になり、依頼の 409 と合わない。
  画面のコードもヘッダーの扱いが増える。

### ぶつかったときの応答（案A・案Bに共通）

- **409 Conflict**、`Content-Type: application/problem+json`。

  ```json
  {
    "type": "about:blank",
    "title": "ほかの担当者が先に状態を変えました",
    "status": 409,
    "detail": "最新の状態を確かめてから、もう一度操作してください",
    "instance": "/api/card-applications/A00000001/status-changes"
  }
  ```

- `errors` は付けない（入力の誤りではないため）。画面は `detail` を表示し、詳細を読み直して最新の状態と履歴を見せる（R12）。
- **許されない遷移（例：申込 → 承認）は 409 にしない**。`version` が合っている（＝画面は今の状態を知っている）のに
  許されない遷移を頼んだのは、リクエストの誤りなので、**400 ＋ `errors[]`（`field: "toStatus"`）**で返す。
  画面は許される遷移のボタンだけを出すので、ふつうは起きない。API では必ず止める（SC-004）。
  - 他の案：遷移の誤りも 409（または 422）にする。状態とぶつかっている、と読むこともできるが、
    楽観ロックの 409 と画面での扱い（読み直すかどうか）が混ざる。エラーの形も、入力の誤りと同じ `errors[]` にしておく方が画面が簡単。
- **確かめる順番**: ① 本文が JSON として読めるか（400）→ ② 入力の項目（担当者名・理由・状態の値・version の形。400）
  → ③ 申込があるか（404）→ ④ version が合うか（409）→ ⑤ 遷移が許されるか（400）→ 保存（`UPDATE` が0行なら 409）。
  ②は DB を読まずに確かめる。②に誤りがあれば、③より後は確かめない。

## R5. 【決めてほしい】年収（0〜9,999万円）の型。constitution の「金額は BigDecimal」に当たるか

**AIの読み方**: 当たる。原則III は「金額は `BigDecimal` で扱わなければならない（MUST）」と書いており、計算に使うかどうかで分けていない。
年収は円で表す額なので、文字どおりに読めば金額にあたる。

### 案A：`BigDecimal`（万円単位、小数なし）。DB は `numeric(4, 0)`（推奨）

- Java は `BigDecimal`（値は万円の数。例：`450` ＝ 450万円）。範囲のチェックは `compareTo` で行う（スキル①の確認5）。
- DB は `numeric(4, 0)` ＋ `CHECK (annual_income BETWEEN 0 AND 9999)`。`BigDecimal` と誤差なくやり取りできる（ADR 0011）。
- JSON は整数の number（`"annualIncome": 450`）。分割払い・リボ払いの金額と同じ返し方。
- 計算・丸めはしない。端数処理のルール（原則IIIの2つ目）は、「万円単位の整数だけを受け付け、丸めない」と data-model.md に書く。
- **理由**:
  - constitution を文字どおりに守れて、例外の説明がいらない。PR のレビューやスキル①で「金額なのに `int`」と言われない。
  - かかる手間は小さい（計算がなく、比べて保存して表示するだけ）。
  - 単位（万円）を型ではなく名前と data-model で示す点は、案Bと同じ。

### 案B：`int`（万円単位）。DB は `integer`

- 整数で、計算も丸めもしないので、誤差は出ない。原則IIIの禁止（`double`・`float`）には当たらない。
- **採らない理由**: 原則IIIの MUST（`BigDecimal`）から外れる。外すなら、Complexity Tracking に理由を書くか、
  constitution を「計算に使う金額は」と直す（改定の手順は PR とレビュー。Day7 の作業としては重い）必要がある。

### 案C：円単位の `BigDecimal`（例：4,500,000）で持つ

- **採らない理由**: spec は万円単位で入力・表示する。円に直す掛け算が1つ増え、変換の誤りの入口が増えるだけ。

## R6. 【提案】テストの DB の片付け方（Testcontainers を共有しているため）

`TestcontainersConfiguration` は、JVM 全体で1つの PostgreSQL を共有している。
申込の表を使うテストが残したデータが、ほかのテスト（「申込が1件もない」「3件が新しい順」など）の結果を変えないようにする。

- **提案**: DB を使うテストのクラスは、**各テストの前に**（`@BeforeEach`）申込の2つの表を空にする。
  - `TRUNCATE card_application_status_history, card_application RESTART IDENTITY`（`JdbcClient` で実行する）。
    申込番号の連番（`card_application_number_seq`）は申込の表の列に `OWNED BY` で結び付けるので、`RESTART IDENTITY` で 1 に戻る。
    テストの申込番号は、毎回 `A00000001` から始まる。
  - この処理は、テスト用の小さな部品（例：`CardApplicationTables.clear(jdbcClient)`）にまとめ、DB を使うテストのクラスがみな呼ぶ。
  - Flyway の履歴の表（`flyway_schema_history`）は消さない。
  - **前に**片付ける理由：前のテストが途中で失敗して残したデータに影響されない。失敗したテストのデータは、次のテストが始まるまで残るので調べられる。
- **理由**:
  - 同時の変更のテスト（2つのスレッドが同じ `version` で変える。R4）は、本当にコミットしないと確かめられない。
    テストを `@Transactional` にして最後に戻すやり方では、このテストが書けない。
  - 戻すやり方では、連番は戻らないので、申込番号を期待値に書けない。
  - 今の DB を使うテスト（`CardPaymentSimulatorApplicationTests`・`HealthEndpointTests`）は申込の表を使わないので、空にしても影響しない。
- **テストが並列で動かないことの確認**（2026-11-25 に確かめた。TRUNCATE がほかのテストのデータを消さないか）:

  | 確かめたこと | 結果 | 意味 |
  |---|---|---|
  | surefire の設定（`pom.xml`、`./mvnw help:effective-pom`） | 3.5.6。`forkCount`・`parallel`・`threadCount` の設定はなく、既定（JVM 1つ、クラスもメソッドも順に実行） | 1回の `./mvnw verify` の中では、DB を使うテストは1つずつ動く |
  | JUnit の並列の設定（`junit-platform.properties`・`@Execution`） | どちらもない。JUnit 5 の並列は既定で切れている | 同上 |
  | Testcontainers の使い回し（`withReuse`・`~/.testcontainers.properties` の `testcontainers.reuse.enable`） | どちらもない | `./mvnw` を2つ同時に動かしても（Stop の hook と手で動かした verify など）、それぞれが自分の PostgreSQL のコンテナを持つ。別の実行のデータは消さない |
  | 1つの JVM の中のコンテナ | `TestcontainersConfiguration` の static の1つを、Spring のコンテキストの間で共有 | 共有はするが、上のとおり順に動くので、TRUNCATE が動いている別のテストとぶつからない |
  | フロントのテスト（Vitest） | ファイルごとに並列で動く | DB を使わない（API は `vi.mock`）ので関係ない |

  **決まり**: DB を使うテストは並列にしない。surefire・JUnit の並列や Testcontainers の使い回しを有効にするときは、
  先にこの片付けの方法を見直す（例：DB を使うテストのクラスに `@ResourceLock("card_application_tables")` を付けて、同時に動かないようにする）。
  今は並列にしていないので、`@ResourceLock` は付けない（原則VIII）。
- **検討した他の案**:
  - テストを `@Transactional` にして、終わったら戻す：書くことは少ないが、上の2つの理由で採らない。
  - `@Sql` で片付けの SQL ファイルを実行する：やっていることは同じ。SQL がテストのコードと別のファイルに分かれるので、上の部品の方を選ぶ。
  - 片付けず、テストごとに違うデータを使い、件数は相対で確かめる：「1件もない」の受け入れシナリオ（US2-6）を確かめられない。

### DB を使うテストと使わないテストの分け方

| 対象 | テストの種類 | DB |
|---|---|---|
| `ApplicationStatus`・`CardApplication`（遷移のルール） | 単体テスト | 使わない |
| 入力チェック（`CardApplicationInputValidator`・`StatusChangeInputValidator`） | 単体テスト（`Clock` を固定する） | 使わない |
| リポジトリ（SQL・楽観ロック・並び順・絞り込み） | `@SpringBootTest` ＋ Testcontainers | 使う（上の片付け） |
| API（contracts との照合、エラーの変換、同時の変更） | `@SpringBootTest` ＋ `@AutoConfigureMockMvc` ＋ Testcontainers | 使う（上の片付け） |

`@JdbcTest`（DB だけを起動するテスト）を使うには、テスト用の依存ライブラリの追加が要るかもしれないので使わない。
`@SpringBootTest` のコンテキストは、設定が同じなら Spring がテストのクラスの間で使い回すので、遅くなりにくい。

## R7. 【提案】申込番号の形式（spec の Assumptions「plan で決める」）

- **提案**: `A` ＋ 8桁の連番（ゼロ埋め）。例：`A00000001`。申込の表の主キーにし、URL にもそのまま使う。
  - DB の連番（`card_application_number_seq`）から、`INSERT` のときに DB が作る（列の既定値）。重ならないことは主キーで守る（FR-004）。
  - 担当者は入力しない。画面とテストの例にも、この形の番号だけを使う（カード番号と見間違えない。原則IV）。
- **理由**: spec の例（「A」＋連番）どおり。8桁で 99,999,999 件まで足りる。固定の長さなので、一覧の並びが見やすい。
- **検討した他の案**: 内部の数の ID（主キー）と、表示用の申込番号を別に持つ。列と連番が2つになるだけで、この機能では得がない。
  UUID は、担当者が読み上げたり探したりしにくい。

| 申込を登録する（US1） | `POST /api/card-applications` | 201 ＋ `Location` ＋ 詳細 |
| 一覧（状態で絞り込み。US2） | `GET /api/card-applications?status=APPLIED` | 200 ＋ `{ "items": [...] }` |
| 詳細（変更履歴を含む。US2） | `GET /api/card-applications/{applicationNumber}` | 200 ＋ 詳細 |
| 状態を変える（US3） | `POST /api/card-applications/{applicationNumber}/status-changes` | 200 ＋ 変更後の詳細 |

- **状態の値**: API と DB は英語の定数（`APPLIED`・`UNDER_REVIEW`・`APPROVED`・`REJECTED`）。画面が日本語の表示名（申込・審査中・承認・否決）に変える。
  日本語を API の値にすると、URL のパラメーターのエンコードやテストの書き方が面倒になる。
- **状態の変更を `POST …/status-changes` にする理由**: 1回の変更で履歴が1行増える（spec FR-018）ので、「変更を1つ作る」と読める。
  `PATCH /api/card-applications/{n}` に `status` を送る形は、「申込の内容は変えられない」（FR-006）と紛らわしい。
- **一覧を配列ではなく `{ "items": [...] }` で返す理由**: Should のページ分け（R13）で `page`・`totalPages` などを**足すだけ**で済み、
  Must の画面のコードを変えずに済む。Should を削るときも、足した項目を外すだけになる。
- **一覧の各行**: 申込番号・氏名（漢字）・状態・申込日時だけ（FR-007）。生年月日などは一覧で返さない（要らない個人情報を画面に出さない）。
- **項目名**: `nameKanji`・`nameKana`・`birthDate`・`annualIncome`・`employerName`・`phoneNumber`、`status`・`appliedAt`・`updatedAt`・`version`、
  履歴は `history[]`（`changedAt`・`fromStatus`・`toStatus`・`staffName`・`rejectionReason`）。状態の変更のリクエストは
  `toStatus`・`staffName`・`rejectionReason`・`version`。

## R9. 【提案】入力チェックの細かいルール（FR-002・FR-016・FR-017）

項目ごとのルールとメッセージは [data-model.md](data-model.md) 2 と contracts の一覧。spec で決まっていない細部だけを書く。

- **文字数の数え方**: コードポイントで数える（`String.codePointCount`）。「𠮷」のような4バイトの文字も1文字。
  PostgreSQL の `varchar(n)` も文字（コードポイント）で数えるので、Java のチェックと DB の上限がそろう。
- **空白だけ**: `strip()`（`InputRules.strip`）は全角スペース（U+3000）も取り除くので、全角スペースだけの入力も未入力になる（spec のエッジケース）。
- **氏名（カナ）に使える文字**: `ァ`〜`ヶ`（U+30A1〜U+30F6）、長音符 `ー`（U+30FC）、全角スペース（U+3000）。
  中黒 `・`、半角カナ、ひらがな、半角スペースは形式の誤りにする（FR-002「全角カタカナと全角スペースだけ」）。
- **生年月日**: `uuuu-MM-dd` の形を `ResolverStyle.STRICT` で読む。2月30日などの存在しない日付は形式の誤り（spec のエッジケース）。
  未来の日付は「未来の日付」のメッセージにし、それ以外で18歳未満・100歳を超えるものは年齢のメッセージにする（R10）。
- **年収**: 半角数字だけ（`InputRules.isInteger`。小数・負の数・カンマは形式の誤り）。長さが20文字を超えるものは範囲の誤り（`isTooLong`。分割払いと同じ）。先頭の0は受け付ける。
- **電話番号**: `0[0-9]{9,10}`（0から始まる10桁か11桁。ハイフンなし）。全角数字は形式の誤り。
- **否決の理由**: 変更後の状態が `REJECTED` のときだけ確かめる。ほかの状態のときに送られても、保存しない（無視する）。
- **担当者名**: 1〜50文字。中身（本当にその人か）は確かめない（ADR 0010、FR-016）。
- **spec との食い違い（2026-11-25 に決定）**: spec US4-1 の例「テスト タロウ」は、姓と名の間が**半角**スペースで、
  FR-002（氏名（カナ）に半角スペースは使えない）と合わなかった。
  **決定**：FR-002 を正とし、spec の例を全角スペース（「テスト　タロウ」）に直した（ユーザーの判断）。テストのデータも全角スペースにする。

## R10. 【提案】日時・申込日・年齢の扱い

- **「今」を `Clock` から取る**: `Clock` を Bean にし、申込日時・更新日時・変更日時と年齢の計算は、すべてそこから取る。
  テストでは時刻を決めた `Clock` に差し替え、18歳・100歳の境界を、日付を固定して確かめる（spec のエッジケース）。
- **タイムゾーンは `Asia/Tokyo` を明示し、サーバーの既定に頼らない**（2026-11-25 にユーザーの指示で足した）:
  - EC2 のコンテナの既定のタイムゾーンはふつう UTC。日本時間の 0:00〜8:59 は、UTC ではまだ前の日なので、既定に頼ると申込日が1日ずれ、
    18歳・100歳の境界の判定を誤る。
  - 日本時間の定数を1か所に置く（`common/time/BusinessTime.JAPAN = ZoneId.of("Asia/Tokyo")`）。
  - `Clock` の Bean は `Clock.system(BusinessTime.JAPAN)`（タイムゾーンを明示する）。
  - 申込日は `LocalDate.ofInstant(clock.instant(), BusinessTime.JAPAN)` で求める。`Clock` のタイムゾーンにも頼らない
    （テストで `ZoneOffset.UTC` の `Clock` を渡しても、日本時間の日付になる）。
  - 本番のコードで `LocalDate.now()`・`LocalDateTime.now()`・`ZoneId.systemDefault()`・`TimeZone.getDefault()`・引数なしの `Instant.now()` を使わない
    （「今」は必ず `Clock` から）。レビューで `grep` して確かめる（tasks の確認の項目）。
  - DB とのやり取りは、`Instant` を `OffsetDateTime`（UTC）にして渡し、読むときも `OffsetDateTime` → `Instant` にする。
    `timestamptz` は時刻そのものを持つので、DB の接続のタイムゾーンでは値が変わらない。生年月日は `date`（`LocalDate`）で、タイムゾーンがない。
  - 画面は `Intl.DateTimeFormat('ja-JP', { timeZone: 'Asia/Tokyo' })` で、ブラウザのタイムゾーンにも頼らない。
- **日付がずれないことを確かめるテスト**（入力チェックの単体テスト。`Clock.fixed(…, ZoneOffset.UTC)` を渡す）:

  | `Clock` の時刻（UTC） | 日本時間 | 申込日 | 生年月日 `2008-11-25` | 生年月日 `1925-11-25` |
  |---|---|---|---|---|
  | `2026-11-24T14:59:59Z` | 11/24 23:59:59 | 2026-11-24 | エラー（17歳） | 登録できる（100歳） |
  | `2026-11-24T15:00:00Z` | 11/25 0:00:00 | 2026-11-25 | 登録できる（18歳） | エラー（101歳） |
  | `2026-11-24T23:59:59Z` | 11/25 8:59:59 | 2026-11-25 | 登録できる（18歳） | エラー（101歳） |
  | `2026-11-25T00:00:00Z` | 11/25 9:00:00 | 2026-11-25 | 登録できる（18歳） | エラー（101歳） |

  2・3行目（日本時間の 0:00〜8:59）は、UTC の日付（11/24）で判定すると結果が逆になる行で、ずれを見つけるためのもの。
  あわせて、`Clock` の Bean のタイムゾーンが `Asia/Tokyo` であることを確かめるテストと、API で登録した `appliedAt` が `Clock` の時刻と同じになるテストを置く。
- **申込日**: 日本時間（`Asia/Tokyo`）の日付。年齢 ＝ `Period.between(生年月日, 申込日).getYears()`（満年齢。spec の Assumptions）。
  2月29日生まれは、うるう年でない年は3月1日に1つ年をとる（`Period.between` の動き）。
- **spec の読み方（2026-11-25 に決定）**: もとのエッジケースは「ちょうど18歳・100歳になる日のとき：登録できる。1日でも外れるとき：入力エラー」。
  100歳の側は、満年齢では「100歳になった日の翌日〜101歳の誕生日の前日」も100歳なので、FR-002 の「100歳以下」と合わなかった。
  **決定**：FR-002 の「100歳以下」（満年齢が100以下）を正とし、上の境界は **101歳になる日でエラー** とする（例は data-model.md 2）。
  spec のエッジケースをそのように直した（ユーザーの判断）。
- **保存**: DB は `timestamptz`。Java は `Instant`。PostgreSQL はマイクロ秒までしか持たないので、`Clock` から取った時刻はマイクロ秒に切り捨ててから保存する
  （保存した値と返した値を同じにする。テストで比べたときにずれない）。
- **API**: 日時は ISO 8601 の UTC（例：`2026-11-25T01:30:00Z`）、生年月日は `YYYY-MM-DD` の文字列。
  画面が `Intl.DateTimeFormat('ja-JP', { timeZone: 'Asia/Tokyo' })` で日本時間にして表示する（FR-011）。
  表示の形は `2026/11/25 00:00`（年/月/日、月・日・時・分は2桁、24時間制）（2026-11-25、analyze の U1 から人が決めた）。
  （Jackson 3 の既定で `Instant` が ISO 8601 の文字列になることは、API のテストで確かめる。）
- **並び順**: 申込日時の新しい順。同じ申込日時が並んだときは、申込番号の大きい順（テストで同じ時刻に登録しても、順番が決まる）。

## R11. 【提案】ダミーのデータ（原則IV、FR-020〜FR-022）

  - 氏名：「テスト 太郎」・「テスト　タロウ」、「見本 花子」・「ミホン　ハナコ」のように、姓を「テスト」「見本」にする。
  - 勤務先：「テスト株式会社」「見本商事」。
  - 電話番号：`0000000000`・`00000000000` のように、0 を並べたもの（形式は通るが、実在しない番号）。
  - 担当者名：「テスト 担当A」・「テスト 担当B」（spec の Assumptions）。
  - 生年月日：テストの `Clock` から計算した境界の日付。
- カード番号は、入力欄・API の項目・DB の列のどこにも作らない（FR-021）。
- 登録の画面に、「ダミーの情報だけを入力してください。本物の氏名・電話番号などは入力しないでください」という注意書きを出す（FR-020）。
- 個人情報をログ・例外のメッセージに出さない。決まりは次の R11-1。

### R11-1. 個人情報をログ・例外のメッセージに出さない決まり（2026-11-25 にユーザーの指示で足した）

対象の個人情報：氏名（漢字・カナ）・生年月日・年収・勤務先名・電話番号・担当者名・否決の理由（理由に個人のことが書かれうるため）。
申込番号・状態・項目名（`nameKana` など）・件数は、個人情報ではないので出してよい。

| # | 決まり | 具体的に |
|---|---|---|
| 1 | アプリのログに、個人情報を書かない | `log.info(request)` のように、リクエスト・ドメインの型をまるごとログに渡さない。ログに書いてよいのは申込番号・状態・項目名・件数だけ。この機能では、ログを書く処理そのものを作らない（要らないため） |
| 2 | 例外のメッセージに、入力の値を入れない | `InputValidationException`・`StatusTransitionException`・`ApplicationNotFoundException`・`StatusConflictException` のメッセージは決まった文と、申込番号・状態・項目名だけ。`"不正な電話番号: " + phone` のような書き方をしない |
| 3 | API のエラーの本文に、入力の値を返さない | Problem Details の `title`・`detail`・`errors[].message` は、contracts のメッセージの一覧の決まった文だけ（入力を埋め込まない） |
| 4 | 個人情報を持つ record の `toString` に、個人情報を出さない | `NewCardApplication`・`CardApplication`・`StatusHistoryEntry`・`*Request` は `toString` を上書きし、申込番号（ないものは型の名前）だけを返す。うっかりログや例外に渡しても漏れないようにする |
| 5 | DB のエラーに、行の中身を入れさせない | PostgreSQL は、制約の違反のとき `DETAIL: Failing row contains (…氏名…)` のように行の値を返し、PostgreSQL の JDBC ドライバーはそれを例外のメッセージに入れる。予期しないエラー（500）のとき、Spring がそのメッセージをログに書く。ドライバーの設定 `logServerErrorDetail=false` で、DETAIL を例外のメッセージに入れないようにする（`application.properties` の `spring.datasource.hikari.data-source-properties.logServerErrorDetail=false`。テストの DB にも同じ設定が効く） |
| 6 | リクエストの中身をログに出す設定を入れない | `spring.mvc.log-request-details`・`logging.level.org.springframework.web=DEBUG`・Tomcat のアクセスログは、既定（出さない）のまま |
| 7 | フロントは `console.log` などで入力や API の結果を出さない | |
| 8 | テストの失敗のメッセージは対象外 | テストのデータは架空の値だけなので（上の決まり）、AssertJ が値を表示してもよい |

確かめ方：

- 4・5 はテストにする。4：各 record の `toString` に、入れた氏名・電話番号が含まれないこと。
  5：入力チェックを通さずにリポジトリで制約に違反する行を入れ（例：年収 10000）、出た例外のメッセージ（原因の例外を含む）に、入れた氏名が含まれないこと。
- 1・2・3・6・7 は、PR の前のレビューで `grep` する（`log\.`・`console\.`・`+ request`・例外の `new …Exception(` の引数）。tasks の確認の項目にする。

Should のキーワード検索（R13）は、キーワード（氏名の一部でありうる）を URL のクエリに入れる。上の 6 のとおりアクセスログは出さないので、サーバーには残らない。
ブラウザの履歴には残りうるが、データは架空の値だけなので受け入れる。

## R13. 【Should】キーワード検索とページ分け（FR-012・FR-013）

## R14. 性能（SC-006：100件で1秒以内）

- 一覧は1回の `SELECT`（状態の条件と `ORDER BY applied_at DESC, application_number DESC`）。Must では全件を返すが、1行は4項目だけなので、100件でも小さい。
- 詳細は申込1行と履歴最大2行。
- 索引は主キーと、履歴の外部キー（`application_number`）だけにする。状態や申込日時の索引は、件数が増えたときに足す（原則VIII）。
- 計測は quickstart.md の手順で、100件を登録してから一覧の応答時間を見る（自動のテストにはしない）。
