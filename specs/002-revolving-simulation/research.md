## R2. 誤差の出ない計算の方法（FR-007・FR-012）

分割払いの R7 のような**式の変形は要らない**。リボ払いは、各回の手数料を順に求めるだけで、累乗も合計の公式も使わないため。

- **決め方（分割払いと同じ考え方）**: 実質年率は小数第1位までなので、k ＝ 実質年率 × 10 は 0〜150 の整数。
  月利 ＝ k ÷ 12,000 なので、各回の手数料は「切り捨て(前回の残高 × k ÷ 12,000)」の整数の割り算1回になる。
  - 実装では、整数の値を持つ `BigDecimal` で掛け算をし、`divide(12000, 0, RoundingMode.DOWN)` で1円未満を切り捨てる。
    丸めは spec FR-007 の「各回の手数料」の1か所だけになる。ほかの項目（支払額・元金・残高・合計）は足し算と引き算だけで、端数は出ない。
  - 分割払いの `InstallmentCalculator` と同じ書き方（k を `intValueExact()` で求め、整数でなければ例外にする）にする。
- **確かめたこと**（2026-11-24、Python の整数で spec FR-007 のとおりに計算した）:
  - spec の受け入れシナリオの値がすべて一致した：100,000円・10,000円・15.0% → 11回・手数料7,497円・支払総額107,497円（返済表11行も一致）、
    同じ条件で0.0% → 10回・0円、1,000円・1,000円・15.0% → 2回（1回目の手数料12円、2回目は12円）、
    10,000,000円・15.0% で 125,000円 → 払い終わらない、126,000円 → 390回、127,000円 → 335回。
  - 利用残高1,000〜20,000円のすべての1円刻み（と10,000,000円）、年率 0.0・0.1・7.5・14.9・15.0%、支払額1,000〜30,000円の
    1,000円刻みのすべての組み合わせで、元金の合計 ＝ 利用残高、支払額の合計 ＝ 支払総額、最終回の残高 ＝ 0、
    元金・残高が負にならない、各回の支払額 ≦ 毎月の支払額 を確かめた。
  - 完済までちょうど360回になる条件の例：949,000円・12,000円・15.0%（360回）。境界の隣は 950,000円・12,000円・15.0%（368回でエラー）。
    テストの境界値に使う（spec のエッジケース「ちょうど360回のとき：計算できる」）。
- **検討した他の案**: 月利を `MathContext` で小数にして掛ける。誤差が出うる（001 の R7 と同じ理由）ので採らない。

## R3. 【提案】API の URL と項目名

- **提案**: `POST /api/revolving-simulations`（001 の R6 で、あとのリボ払いの URL として挙げていたもの）。
  - リクエスト：`balance`（利用残高）・`monthlyPayment`（毎月の支払額）・`annualRate`（実質年率。分割払いと同じ名前）。3項目とも文字列。
  - レスポンス：`paymentCount`（完済までの支払回数）・`totalFee`・`totalPayment`・`schedule[]`。
    `schedule[]` の項目（`number`・`payment`・`principal`・`fee`・`balanceAfter`）は分割払いと同じにする。
- **理由**:
  - 項目の意味が同じもの（実質年率・手数料の合計・支払総額・返済表の行）は、分割払いと同じ名前にすると、画面の部品と型を共通にできる（R6）。
  - 利用残高は、分割払いの「利用金額（`amount`）」と意味が違う（すでにある残高）ので、別の名前にする。
  - 完済までの支払回数は、分割払いでは入力の `paymentCount` と同じ意味なので、同じ名前を出力に使う。
- **検討した他の案**: `amount`（利用残高を分割払いと同じ名前にする）。共通にしやすいが、spec の言葉（利用残高）と API の名前がずれる。

## R4. 【提案】毎月の支払額のチェックの順番と、計算が要るチェック（FR-004）

FR-004 の条件のうち、「1回目の手数料以下」と「360回を超える」は、ほかの2項目（利用残高・実質年率）が正しくないと確かめられない。
また「利用残高以下」は、利用残高が正しくないと確かめられない。

- **提案**: 毎月の支払額は、次の順に確かめ、最初に当てはまった1つを返す（分割払いの「必須 → 形式 → 範囲」のあとに、ほかの項目との関係を足す）。

  | 順 | チェック | 確かめる条件 |
  |---|---|---|
  | 1 | 必須 | いつも |
  | 2 | 形式（半角数字だけ） | いつも |
  | 3 | 範囲と単位（1,000以上・10,000,000以下・1,000円単位・20文字以内） | いつも |
  | 4 | 利用残高以下 | 利用残高が 1〜3 を通ったとき |
  | 5 | 1回目の手数料より大きい | 3項目すべてが 1〜4 を通ったとき |
  | 6 | 完済までの回数が360回以内 | 5 を通ったとき |

  - 3 の上限 10,000,000円は、利用残高の上限と同じ。利用残高が誤っていて 4 を確かめられないときにも、明らかに大きすぎる値を止めるため。
  - 5・6 は、1〜4 で誤りが1つでもあれば確かめない。そのときは、1〜4 で見つかった誤りだけを返す（どれも直さないと 5・6 は確かめられない）。
  - 5 に当たる条件は 6 にも当たる（払い終わらない）。直し方が違うので、5 を先に確かめて別のメッセージにする。
- **計算が要るチェック（5・6）の作り方**:
  - **提案**: 計算（`RevolvingCalculator`）が「払い終わらない」ことを見つけたら、ドメインの例外 `RevolvingNotPayableException`
    （理由：`FEE_NOT_COVERED`・`TOO_MANY_PAYMENTS`）を投げる。Web 層（`RevolvingInputValidator`）が、その理由を `monthlyPayment` の
    入力エラーのメッセージに変える。
    - 計算は1回で済む（チェックのために計算して、もう一度結果を計算することがない）。
    - 「払い終わらないかどうか」の判断は計算（ドメイン）に、利用者に見せる文言は Web 層に置く。分割払いと同じく、メッセージは Web 層だけにある。
    - 計算は、どう呼ばれても361回目に入る前に止まるので、終わらない計算にならない（SC-005）。
  - **検討した他の案**: 入力チェックの中で、計算とは別に「1回目の手数料」と「完済までの回数」を求める。入力チェックだけで完結するが、
    回数を求める繰り返しが計算と二重になり、ずれるおそれがある。
- **エラーの並び**: `errors` は `balance` → `monthlyPayment` → `annualRate` の順（spec FR-001 の入力の順）。

## R5. 【提案】エラーのメッセージの文言

一覧は [contracts/revolving-simulation-api.md](contracts/revolving-simulation-api.md)。決め方は次のとおり。

- 利用残高：分割払いの利用金額のメッセージの「利用金額」を「利用残高」にしたもの（範囲も同じ）。
- 実質年率：分割払いとまったく同じ（spec FR-003「分割払いとそろえる」）。共通の処理にする（R6）。
- 毎月の支払額：
  - 範囲と単位は1つのメッセージにまとめる（「1,000円以上10,000,000円以下の、1,000円単位」）。spec US3-3 の「入力できる額の条件」を1文で示せる。
  - 5（1回目の手数料以下）と 6（360回超）は、spec US3-4・US3-5 のとおり、理由と直し方（支払額を増やす）を書く。
  - 手数料や必要な支払額の具体的な金額は入れない（メッセージが条件ごとに変わり、テストと説明が増える。原則VIII）。

移したあとも、分割払いの既存のテストがそのまま通ることで確かめる（原則I の refactor）。
テストは、移した先の型・ファイルを使うように import とファイルの場所だけを直し、確かめる内容は変えない。

## R7. 【提案】2つの機能を1つの画面でどう切り替えるか

今の画面は、見出し「分割払いシミュレーション」と分割払いのフォームだけ。ルーター（画面の遷移）は入れないと決めてある（001 の plan.md、原則VIII）。

- **提案**: 画面の上にタブ（「分割払い」「リボ払い」）を置き、`App` の state で切り替える。最初は「分割払い」を表示する。
  - 見出しは「カード支払シミュレーション」に変える。
  - タブは WAI-ARIA の tabs の形（`role="tablist"`・`tab`・`tabpanel`、`aria-selected`）にし、画面のテストでは role で探す。
  - 表示していないほうのフォームは描画しない（切り替えると、入力と結果は消える）。2つのフォームで同じ `id`（`annualRate`）を使っても、ぶつからない。
- **理由**: ライブラリが要らず、URL も変わらない。申込管理（Day7）でタブを1つ足せば済む。
- **検討した他の案**:

| 案 | 採らなかった理由 |
|---|---|
| 2つの機能を縦に並べる | タブより簡単だが、画面が長くなり、返済表（最大360行）の下に分割払いが隠れる。入力欄の `id` が重なるので、付け直しが要る |
| ルーター（React Router など）で URL を分ける | ライブラリが増える。この MVP では URL を分ける必要がない（原則VIII） |
| 切り替えても入力と結果を残す | 両方を描画したまま隠す必要があり、テストと `id` の扱いが増える。spec に求めがない |

## R8. 性能（SC-005）

- 返済表は最大360行。各行は掛け算1回と割り算1回なので、計算は1ミリ秒未満で終わる。分割払いと同じく API を呼んでも1秒以内に十分おさまる。
- 支払総額は「360回 × 毎月の支払額（10,000,000円以下）」以下なので、どんな入力でも36億円を超えない
  （例：10,000,000円・127,000円・15.0% で約4,244万円）。JavaScript の数値が誤差なく扱える整数の範囲に十分おさまる（001 の R6 と同じ判断）。
- 360行の表は、そのまま描画する（ページ分けや仮想スクロールは spec にないので作らない。原則VIII）。
