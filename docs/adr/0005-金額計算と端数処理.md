# 0005 金額計算と端数処理

## 状態

Accepted（2026-11-17）

## 背景

- constitution 原則III：金額は`BigDecimal`で扱い、`double`・`float`を使ってはならない。端数処理のルール（丸め方・桁数・どの段階で丸めるか・端数をどこに寄せるか）は、各機能の仕様に明記する。
- 浮動小数点の誤差や丸めの不一致は、利用者に見せる金額の誤りに直結し、後から気づきにくい（constitution 原則III の理由）。
- 金額は1円単位で表示する。1円未満の端数が出るので、どこかの回でその差を回収する必要がある。

## 決定

| 項目 | 決定 |
|---|---|
| 金額の型 | `BigDecimal`。途中で誤差を出さず、丸めは仕様に書いた箇所でだけ明示的に行う |
| 丸め方 | 1円未満を切り捨てる |
| 月利 | 実質年率 ÷ 12（日割り計算はしない） |
| 分割払い | 元利均等方式。支払総額を回数で割った端数は**初回に寄せる**。返済表の毎回の手数料を切り捨てた分は最終回の手数料にまとめる |
| リボ払い | **元利定額方式**（毎月の支払額は手数料込みの定額）。最終回は「前回の支払後の残高＋その回の手数料」を払う |

計算式と各項目の端数処理の詳細は、各機能の仕様を正とする。

- 分割払い：`specs/001-installment-simulation/spec.md` FR-006・FR-007・FR-011
- リボ払い：`specs/002-revolving-simulation/spec.md` FR-006〜FR-008・FR-012

選んだ理由：

- 日本のカード会社で多い方式である。
- 1円未満の端数は、どこかの回で回収する必要がある（支払額の合計を支払総額と一致させる）。
- 分割払いの初回寄せ：日本のカード会社で多いやり方で、利用者と上司に説明しやすい。
- リボ払いの元利定額方式：日本で最も一般的で、毎月の支払額が一定でわかりやすい。

## 検討した他の案

| 案 | 採らなかった理由 |
|---|---|
| 金額を`double`で計算する | constitution 原則III で禁止。誤差が出る。 |
| 四捨五入 | 日本のカード会社で多い方式は切り捨てであるため。 |
| 分割払いの端数を最終回に寄せる | 返済表の計算は素直になるが、日本のカード会社で多いやり方（初回寄せ）から離れる。 |
| リボ払いを元金定額方式にする | 元利定額方式の方が日本で最も一般的で、毎月の支払額が一定でわかりやすい。 |
| リボ払いを残高スライド方式にする | リボ払いの仕様で範囲外とした。 |
| 日割りで手数料を計算する | 仕様で範囲外とした（締め日・支払日・日割りは扱わない）。 |

## 結果

### 良い影響

- 支払額の合計が、必ず支払総額と一致する。
- 端数処理が仕様に書かれているので、テストの期待値を仕様から直接作れる。
- 自作スキル①（金額計算のレビュー）の照合先になる（`docs/sprint-plan.md`）。

### 悪い影響

- `BigDecimal`はコードが長くなり、丸めの指定を忘れると例外や意図しない桁になる。レビューとテストで確かめる必要がある。
- 分割払いでは、利用金額が小さく回数が多いとき、最終回の手数料が他の回より大きくなることがある（分割払いの仕様のエッジケース）。
- 日割りをしないので、実際のカード会社の請求額とは一致しない（シミュレーターとしての近似）。
