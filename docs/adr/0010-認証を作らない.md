# 0010 認証を作らない

## 状態

Accepted（2026-11-17）

## 背景

- MVPの範囲外のものは作らない（constitution 原則VIII）。範囲は各機能の仕様で定める。
- 3機能すべての仕様で、認証・ログインを範囲外としている。
  - `specs/001-installment-simulation/spec.md`、`specs/002-revolving-simulation/spec.md`：範囲外
  - `specs/003-card-application/spec.md`：範囲外（担当者を区別しない）
- 申込管理は、カード会社の担当者だけが使う。申込のデータはダミー（明らかに架空と分かるもの）だけを使う（constitution 原則IV、申込管理の仕様 FR-020・FR-022）。
- アプリはEC2で公開する（[0009](0009-デプロイ構成.md)）。

## 決定

- このスプリントでは、認証・ログインを作らない。
- 代わりに、EC2のセキュリティグループでアクセス元のIPアドレスを制限する。
- 申込の状態を変えるときの担当者名は、自己申告とする（申込管理の仕様 FR-016）。

選んだ理由：

- 3機能の仕様で範囲外としており、MVPの範囲外は作らない（constitution 原則VIII）。
- 扱うデータはダミーだけである（constitution 原則IV）。

## 検討した他の案

| 案 | 採らなかった理由 |
|---|---|
| このスプリントで認証を作る | 仕様で範囲外。限られた期間で、説明できる品質のMVPを確実に届けるため（constitution 原則VIII）。 |
| 認証もIP制限もせずに公開する | URLを知っている人なら誰でも、申込データを見たり変えたりできる。データはダミーでも、カード業務アプリとして説明できない。 |

## 結果

### 良い影響

- 3機能の本体と品質基準（TDD・カバレッジ・hooks）に時間を使える。

### 悪い影響

- 担当者名は自己申告になる。別の人がほかの担当者の名前を入力しても、システムは見分けられず、入力された名前のまま履歴に残る（申込管理の仕様 FR-016・エッジケース）。
- 誰が操作したかを、システムとしては保証できない。
- 許可したIPアドレスから届く人は、誰でもすべての機能を使える。
- IPアドレスが変わると、セキュリティグループの設定を直す必要がある。

### 次のスプリントでの対応

- Spring Securityで、最小限のログインを入れる。
- 状態を変えた担当者は、自己申告の担当者名をやめ、ログイン中のユーザーから自動で記録する形に置き換える。
