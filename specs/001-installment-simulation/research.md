## R1. Java のバージョン

- **決定**: Java 25（LTS）
- **理由**:
  - 現在の最新のLTS（2025年9月リリース）で、サポート期間が長い。
  - Codespaces に、すでに OpenJDK 25.0.5（Microsoft Build）が入っている。入れ直しが要らない。
  - Spring Boot 4 系（R2）が Java 25 に対応している。
- **気をつけること**:
  - ビルドに使うツールも Java 25 に対応している版を使う必要がある。
    特にカバレッジ計測の JaCoCo は 0.8.14 以降が必要（2026-11-17 時点の最新は 0.8.16）。
  - EC2 で動かすコンテナのイメージ（[ADR 0009](../../docs/adr/0009-デプロイ構成.md)）も Java 25 にそろえる。
- **検討した他の案**:

| 案 | 採らなかった理由 |
|---|---|
| Java 21（LTS） | 情報や事例は多いが、Codespaces に入っていないので入れ直しが要る。新しく始めるプロジェクトで、1つ前のLTSを選ぶ理由が弱い。 |
| Java 17（LTS） | Spring Boot 4 の最低要件ではあるが、古く、選ぶ理由がない。 |

## R2. Spring Boot のバージョン

- **決定**: Spring Boot 4.1 系に固定する（2026-11-17 時点の最新は 4.1.2）。パッチは作成時点の最新を使う。
  4.2 は 11/19 リリース予定だが、スプリント中は乗り換えない。
- **理由**:
  - 現在の最新の系列で、OSSのサポート期間が残っている。
  - Java 25（R1）に対応している。
  - ビルドに使う `spring-boot-starter-parent` の版を1か所で決めれば、依存ライブラリの版もそろう。
- **気をつけること（悪い影響）**:
  - Spring Boot 4 では、JSON のライブラリが Jackson 3 になり、パッケージ名が変わった（`com.fasterxml.jackson` → `tools.jackson`）。
    ネット上の情報の多くは Spring Boot 3（Jackson 2）向けなので、そのまま使えないことがある。
  - スターターやテスト用のモジュールの名前が、3 系から一部変わっている（例：`spring-boot-starter-webmvc`）。
- **検討した他の案**:

| 案 | 採らなかった理由 |
|---|---|
| Spring Boot 4.0 系 | 4.1 系がすでに出ており、4.0 系を選ぶ理由がない。 |
| Spring Boot 3.5 系 | 情報は多いが、OSSのサポート期間がすでに終わっているか、終わりが近い（公式のサポート表で要確認）。新しく作るのに古い系列を選ぶ理由が弱い。 |

## R5. リポジトリのフォルダ構成

- **決定（案A）**: ルートを Spring Boot のプロジェクトにし（`pom.xml`・`src/`）、フロントエンドは `frontend/` に置く。
  `pom.xml` は1つだけ。

  ```text
  pom.xml            # 唯一の pom。フロントのビルドもここから呼ぶ
  mvnw, .mvn/        # Maven Wrapper
  src/               # バックエンド（Spring Boot）
  frontend/          # フロントエンド（React＋Vite）。package.json はここ
  docs/  specs/      # 既存
  ```

- **理由**:
  - `pom.xml` が1つで済み、設定が一番少ない（constitution 原則VIII、[ADR 0002](../../docs/adr/0002-ビルドツール.md) の「設定に時間をかけられない」）。
  - Spring Boot の標準の配置（`src/main/java`）のままなので、Spring Initializr で作ったものをそのまま使え、情報も探しやすい。
  - フロントは `frontend/` に分かれているので、「フロントとバックを分けている」ことはフォルダを見れば説明できる（[ADR 0001](../../docs/adr/0001-技術スタック.md)）。
  - `mvn package` 1回で、フロントを同梱した1つの jar ができる（constitution 原則V、[ADR 0003](../../docs/adr/0003-リポジトリと成果物.md)）。
- **悪い影響**:
  - ルートにバックエンドのファイルと `frontend/` が並ぶので、案Bほど左右対称には見えない。
- **検討した他の案**:

| 案 | 内容 | 採らなかった理由 |
|---|---|---|
| 案B：Maven のマルチモジュール | ルートに親の `pom.xml`、`backend/pom.xml`・`frontend/pom.xml` を置く | 見た目は対称で分かりやすいが、pom が3つになり、モジュール間で成果物を受け渡す設定が要る。期間に対して設定が重い。 |
| 案C：`backend/` と `frontend/` を並べ、pom は `backend/` だけ | `backend/pom.xml` から `../frontend` をビルドする | ルートで `mvn` が動かず、毎回 `-f backend` や `cd` が要る。CI・Docker のビルドでも同じ手間がかかる。 |
| 案D：フロントを `src/main/frontend/` に置く | Maven の中にフロントを入れる | フロントの開発（`npm run dev` など）で深いフォルダに移動する必要がある。フロントとバックの境界がフォルダから見えにくい。 |

### フロントのビルド結果を jar に入れる方法

- **決定**: Vite は `frontend/dist/` に出力する（Vite の標準）。Maven が `frontend/dist/` を
  `target/classes/static/` にコピーし、Spring Boot が静的ファイルとして配信する。
- **理由**: フロントの設定（`vite.config.ts`）がバックエンドのフォルダ構成を知らずに済み、フロント単体でもビルドできる。
- **検討した他の案**: Vite の出力先を `../target/classes/static` に直接向ける。設定は1つ減るが、
  フロントの設定がバックエンドの都合に依存し、`mvn clean` との順番でファイルが消えることがある。
- 具体的な設定（frontend-maven-plugin の実行タイミング、テストの組み込み）は Day3 のタスクで作る。

### 開発中の画面とAPIのつなぎ方

- **決定**: 開発中は Vite の開発サーバーの proxy で、`/api` へのリクエストを Spring Boot（`localhost:8080`）に転送する。
- **理由**: 本番（1つの jar）と同じく、画面から見て同じオリジンになる。CORS の設定が要らない（原則VIII）。

### Java のパッケージ構成

- **決定**: 機能ごとにパッケージを分ける（`installment`・あとで `revolving`・`application`）。
  機能の中で「計算（ドメイン）」と「API（Web）」を分ける。
- **理由**: 3機能が互いに依存しないので、機能単位でまとまっている方が、読む範囲が狭く済む。
  計算をWebから切り離すと、計算のテストを Spring を起動せずに速く回せる（原則I の red → green を速くする）。
- **検討した他の案**: 層ごと（`controller`・`service`・`model`）に分ける。よく見る形だが、1つの機能を読むのに複数のパッケージを行き来する。
- パッケージ名のルートは `com.example.cardpayment`。

## R6. APIの形

詳細は [contracts/installment-simulation-api.md](contracts/installment-simulation-api.md)。ここでは選んだ理由を書く。

### URL とメソッド

- **決定**: `POST /api/installment-simulations`。成功は `200 OK`、入力エラーは `400 Bad Request`。
- **理由**:
  - `/api` で始めることで、画面（静的ファイル）と API の URL がぶつからない。開発中の proxy（R5）も `/api` だけを転送すればよい。
  - 入力を JSON の本文で送れるので、リクエストとエラーの形を、あとのリボ払い（`/api/revolving-simulations`）とそろえやすい。
  - 何も保存しないので `201 Created` ではなく `200 OK` を返す。
- **検討した他の案**:

| 案 | 採らなかった理由 |
|---|---|
| `GET /api/installment-simulation?amount=...&paymentCount=...&annualRate=...` | 計算だけで副作用がないので意味としては合う。ただし入力をクエリ文字列で受けると、未入力・形式の誤りの扱いがフレームワークの変換に左右され、項目ごとのエラーメッセージ（FR-005）を作りにくい。 |
| `POST /api/installments/simulate`（動詞のURL） | 動きとしては分かりやすいが、REST の名前の付け方（名詞）から外れる。大きな差はない。 |

### リクエストの項目を文字列で受ける

- **決定**: `amount`（利用金額）・`paymentCount`（支払回数）・`annualRate`（実質年率）を、
  **画面に入力されたままの文字列**で受け取り、サーバー側で厳密に解釈する。
- **理由**:
  - 仕様のエッジケース「小数・負の数・数字以外」「12.25% は勝手に丸めずエラー」を、すべて項目ごとのメッセージにできる（FR-005、SC-004）。
  - JSON の数値で受けると、JSON の変換の段階でエラーになったり（`"abc"`）、設定によっては小数が整数に切り捨てられたり（`1000.5` → `1000`）して、どの項目が悪いかを返せない・勝手に丸まるおそれがある。
  - 入力チェックがサーバーの1か所にまとまり、フロントとバックで同じチェックを二重に作らずに済む（R8）。
- **検討した他の案**: JSON の数値で受け、Java の `BigDecimal` に変換して Bean Validation（`@Digits` など）で確かめる。
  APIとしては素直だが、上の「変換の段階のエラー」を別に扱う必要があり、フロントでも数字以外を弾く処理が要る。

### レスポンスの金額を JSON の整数で返す

- **決定**: 金額はすべて円単位の整数（JSON の number）で返す。
- **理由**:
  - 金額は1円単位で、最大でも約1,160万円（10,000,000円・36回・15.0%の支払総額）。JavaScript の数値が誤差なく扱える整数の範囲（約9千兆）に十分おさまる。
  - フロントは金額を**計算しない**で、3桁区切りで表示するだけにする（FR-014）。計算はすべてサーバーの `BigDecimal` で行う（原則III、[ADR 0001](../../docs/adr/0001-技術スタック.md) の「JavaScript の数値は浮動小数点」）。
- **検討した他の案**: 金額を文字列で返す。どんな桁数でも安全だが、この機能の金額の範囲では必要がなく、フロントで毎回変換が要る。

### エラーの形

- **決定**: RFC 9457（Problem Details）の形で返し、項目ごとのエラーを `errors` の配列に入れる。
- **理由**: Spring に標準で入っている形（`ProblemDetail`）で、作るものが少ない。申込管理など、あとの機能のエラーも同じ形にそろえられる。
- **検討した他の案**: 独自の形（`{"errors": {...}}` だけ）。少し短いが、標準の形を使わない理由がない。

## R7. 誤差の出ない計算の方法（FR-006・FR-011）

仕様は「途中で誤差の出ない方法」で計算し、丸めは決めた箇所だけで行うことを求めている（原則III）。
ところが月利 ＝ 実質年率 ÷ 12 は、たとえば 14.9% のとき 0.0124166… と割り切れず、
`BigDecimal` でもそのまま割ると、どこかの桁で丸めることになる。

- **決定**: 割り算を最後の1回にまとめ、それまでは整数だけで計算する。
  - 実質年率は小数第1位までなので、k ＝ 実質年率 × 10 は 0〜150 の整数になる。月利 r ＝ k ÷ 12,000。
  - D ＝ 12,000、A ＝ (D ＋ k)^n、B ＝ D^n とおくと、(1 ＋ r)^n ＝ A ÷ B なので、仕様の式は次のように整数の割り算1回で書ける。

    手数料の総額 ＝ 切り捨て( (n × P × k × A − P × D × (A − B)) ÷ (D × (A − B)) )　（P ＝ 利用金額）

  - 返済表の手数料（最終回の1つ前まで）は ＝ 切り捨て( 前回の残高 × k ÷ 12,000 )。これも整数の割り算1回。
  - 実装では、整数の値を持つ `BigDecimal` で掛け算・引き算をし、最後に `divide(除数, 0, RoundingMode.DOWN)` で
    1円未満を切り捨てる。この割り算は、正確な商を切り捨てた値を返すので、丸めは仕様の箇所の1回だけになる。
- **確かめたこと**: この方法を Python の整数で書いて計算し、仕様の受け入れシナリオ
  （100,000円・12回・15.0%の返済表12行と合計、1,000円・36回・15.0%、100,000円・3回・0.0%）の値がすべて一致した。
  また、利用金額 1,000〜5,000円のすべてと上限付近、全11種類の支払回数、0.0〜15.0%のすべての年率で、
  元金・残高が負にならず、最終回の残高が0円になることを確かめた。
- **理由**: 仕様の FR-011 を文字どおり満たせる。丸めの箇所がコードの上で1か所ずつ見えるので、レビュー（自作スキル①）で確かめやすい。
- **気をつけること**: 仕様の式を変形している（変形は人がレビューして採用した）。テストの期待値は変形後の式ではなく、仕様の表から作る。
- **検討した他の案**:

| 案 | 採らなかった理由 |
|---|---|
| `MathContext`（例：34桁）で月利と累乗を計算する | 誤差はごく小さいが、ゼロではない。真の値がちょうど整数のときや、整数のすぐ下のときに、切り捨ての結果が1円ずれるおそれがあり、FR-011 を文字どおりには満たさない。 |
| `double` で計算する | constitution 原則III で禁止。 |

## R8. 入力チェックをどこで行うか

- **決定**: 入力チェックはサーバー（API）で行い、その結果を正とする。フロントは、API が返した項目ごとのメッセージを、その入力欄のすぐ下に赤字で表示する（ポップアップは使わない）。
- **理由**:
  - チェックのルール（FR-002〜FR-004）とメッセージが1か所にまとまり、ずれない。
  - 入力してから結果が出るまで1秒以内（SC-005）は、計算が軽いのでAPIを呼んでも十分に満たせる。
- **フロントで行うこと**: 支払回数は選択肢（FR-003 の11種類）から選ぶ形にする。それ以外のチェックはしない。
- **検討した他の案**: フロントでも同じチェックを行い、APIを呼ぶ前に止める。反応は速くなるが、同じルールを Java と TypeScript で二重に作り、テストも二重になる（原則VIII）。

## R9. テストの方法

- **バックエンド**:
  - 計算（`InstallmentCalculator`）：JUnit 5 ＋ AssertJ。Spring を起動しない単体テスト。
    - 仕様の受け入れシナリオ（返済表の全行を含む）を、そのままテストの期待値にする。
    - 上限・下限・年率0%・端数が出る条件（SC-002）。
    - FR-008〜FR-010 の性質（支払額の合計＝支払総額、元金の合計＝利用金額、最終回の残高＝0円）を、
      多くの条件の組み合わせ（`@ParameterizedTest`）で確かめる（SC-003）。
  - 入力チェック：境界値（999／1,000／10,000,000／10,000,001円、4回、−0.1／0.0／15.0／15.1%、12.25%、未入力、数字以外）。
  - API：MockMvc（`@WebMvcTest`）で、200 と 400 のレスポンスの形を [contracts](contracts/installment-simulation-api.md) と照らし合わせる。
- **フロントエンド**: Vitest ＋ React Testing Library ＋ jsdom。
  - API の呼び出しはモジュールごと差し替え（`vi.mock`）、画面の動き（入力 → 結果の表示、エラーの表示、再実行で前回の結果が消える）を確かめる。
  - 金額の3桁区切り（FR-014）、初回と2回目以降の分け方（FR-012）。
  - 検討した他の案：MSW で API をまねる。本物に近いが、依存ライブラリが増える（原則VIII）。
- **カバレッジ**: 計測ツールと除外対象は ADR 0006（Proposed）で Day3 に決める。候補は JaCoCo と @vitest/coverage-v8。この機能はそれに従う。

## R10. DB を使わないこと

- **決定（前提どおり）**: この機能は計算だけで、DB は使わない。保存もしない（spec の Assumptions）。
- **気をつけること**: あとで申込管理のために DB のライブラリ（JPA・Flyway・PostgreSQL のドライバー）を入れると、
  Spring Boot は起動時に DB への接続を求める。分割払いのテスト（特に `@WebMvcTest` と計算の単体テスト）は
  DB なしで動く形にしておき、申込管理を作るときに DB の設定を足す。
  分割払いの段階では、DB のライブラリを入れない（原則VIII）。
