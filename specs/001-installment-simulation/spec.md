# 機能仕様：分割払いの支払シミュレーション

**Feature Branch**: `001-installment-simulation`

**Created**: 2026-11-17

**Status**: Planned

**Input**: User description: "クレジットカードの分割払いシミュレーション機能。カード利用者が、分割払いにしたときの毎月の支払額と手数料を事前に確認できるようにする。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 毎月の支払額と手数料を事前に確かめる (Priority: P1)

カードの利用者が、利用金額・支払回数・実質年率を入力すると、毎月いくら払うのか、
手数料が合計いくらかかるのか、全部でいくら払うのかを、分割払いにする前に確かめられる。

**Why this priority**: この機能の目的そのもの。これだけで、利用者は分割払いにするかどうかを判断できる。

**Independent Test**: 利用金額・支払回数・実質年率を入力してシミュレーションを実行し、
毎月の支払額・手数料の合計・支払総額が、手計算した期待値と1円単位で一致することで確かめられる。

**Acceptance Scenarios**:

1. **Given** 利用金額100,000円・支払回数12回・実質年率15.0%を入力した状態, **When** シミュレーションを
   実行する, **Then** 手数料の合計は8,309円、支払総額は108,309円、初回の支払額は9,034円、
   2回目以降の支払額は9,025円と表示され、支払総額 ＝ 利用金額 ＋ 手数料の合計 が成り立つ
2. **Given** 1円未満の端数が出る条件を入力した状態, **When** シミュレーションを実行する,
   **Then** 端数は FR-006 のルールどおりに扱われ、差額は初回に寄せられ、表示される金額はすべて1円単位である
3. **Given** 利用金額100,000円・支払回数3回・実質年率0.0%を入力した状態, **When** シミュレーションを
   実行する, **Then** 手数料の合計は0円、支払総額は100,000円、初回は33,334円、2回目以降は33,333円である

### User Story 2 - 返済表で回ごとの内訳を見る (Priority: P2)

利用者が、1回目から最終回までの各回について、支払額・そのうちの元金と手数料・
支払後の残高を、返済表で確かめられる。

**Why this priority**: 残高がどう減っていくかが分かり、納得して選べる。ただし、P1だけでも判断はできる。

**Independent Test**: シミュレーションの結果に、支払回数と同じ行数の返済表が表示され、
各列の合計と最終回の残高が FR-008〜FR-010 を満たすことで確かめられる。

**Acceptance Scenarios**:

1. **Given** 支払回数12回でシミュレーションを実行した状態, **When** 返済表を見る,
   **Then** 1回目から12回目までの12行があり、各行に回・支払額・手数料・元金・支払後の残高がある

4. **Given** 返済表を表示した状態, **When** 最終回の行を見る, **Then** 支払後の残高は0円である

### User Story 3 - 誤った入力に気づいて直す (Priority: P3)

利用者が、未入力の項目や範囲外の値を入力してシミュレーションを実行すると、
計算は行われず、どの項目をどう直せばよいかが分かる。

**Why this priority**: 誤った結果を見せないために必要。正しい入力の流れ（P1）が先にあって意味を持つ。

**Independent Test**: 未入力・範囲外・形式の誤りの各入力でシミュレーションを実行し、
結果が表示されず、項目ごとのエラーメッセージが表示されることで確かめられる。

**Acceptance Scenarios**:

1. **Given** 利用金額が未入力の状態, **When** シミュレーションを実行する,
   **Then** 結果は表示されず、利用金額の項目に「入力してください」という趣旨のメッセージが表示される
2. **Given** 利用金額が上限を1円超えている状態, **When** シミュレーションを実行する,
   **Then** 結果は表示されず、入力できる範囲がメッセージで示される
3. **Given** 複数の項目が誤っている状態, **When** シミュレーションを実行する,
   **Then** 誤っているすべての項目に、それぞれのメッセージが表示される

---

### Edge Cases

- 実質年率が0%のとき：手数料は0円になり、支払総額は利用金額と一致する
- 利用金額・支払回数・実質年率が、上限ちょうど・下限ちょうどのとき：計算できる
- 上限を1単位超える・下限を1単位下回るとき：入力エラーになる
- 利用金額に小数・負の数・数字以外の文字が入力されたとき：入力エラーになる
- 実質年率に、小数第2位以下の値（例：12.25%）が入力されたとき：入力エラーになる（勝手に丸めない）
- 支払回数に、一覧にない回数（例：4回）が指定されたとき：入力エラーになる
- 支払総額が支払回数で割り切れないとき：FR-006 のとおりに差額を初回に寄せ、支払額の合計が支払総額と一致する
- 毎回の手数料を切り捨てた分は、最終回の手数料にまとめて加わる。利用金額が小さく回数が多いときは、
  最終回の手数料がその回の元金より大きくなることがある（例：1,000円・36回・15.0%）
- 入力を直して再度実行したとき：前回の結果は残らず、新しい結果だけが表示される

## Requirements *(mandatory)*

### Functional Requirements

**入力**

- **FR-001**: 利用者は、利用金額（円）・支払回数・実質年率（%）を入力できなければならない。3項目とも必須とする。
- **FR-002**: 利用金額は1円単位の整数で、1,000円以上10,000,000円以下でなければならない。
- **FR-003**: 支払回数は、3・5・6・10・12・15・18・20・24・30・36回のいずれかでなければならない。
- **FR-004**: 実質年率は0.0%以上15.0%以下で、小数第1位までの値でなければならない。
- **FR-005**: 入力が FR-001〜FR-004 を満たさないとき、システムは計算を行わず、誤っているすべての項目に、
  直し方が分かるメッセージを表示しなければならない。

**計算**

- **FR-006**: システムは、次の「手数料の計算方式と端数処理のルール」に従って計算しなければならない。
  以下、月利 ＝ 実質年率 ÷ 12、n ＝ 支払回数とする。

  | 項目 | 計算方法 | 端数処理 |
  |------|----------|----------|
  | 手数料の合計 | 元利均等方式で毎月の支払額を端数なしで求め（利用金額 × 月利 × (1＋月利)^n ÷ ((1＋月利)^n − 1)）、それに n を掛けて利用金額を引く | 1円未満を切り捨てる |
  | 支払総額 | 利用金額 ＋ 手数料の合計 | 端数は出ない |
  | 毎月の支払額（2回目以降） | 支払総額 ÷ n | 1円未満を切り捨てる |
  | 毎月の支払額（初回） | 支払総額 −（2回目以降の支払額 ×（n − 1）） | 端数は出ない（差額は初回に寄せる） |
  | 返済表の手数料（1回目〜最終回の1つ前） | 前回の支払後の残高 × 月利（1回目は利用金額 × 月利） | 1円未満を切り捨てる |
  | 返済表の手数料（最終回） | 手数料の合計 − それまでの各回の手数料を足したもの | 端数は出ない |
  | 返済表の元金 | 各回の支払額 − その回の手数料 | 端数は出ない |
  | 支払後の残高 | 前回の支払後の残高 − その回の元金 | 端数は出ない |

- **FR-007**: 実質年率が0.0%のときは、FR-006 の元利均等方式の式を使わず、次のとおりとする。
  手数料の合計と返済表の手数料はすべて0円。毎月の支払額は「利用金額 ÷ n」の1円未満を切り捨て、
  余りは初回に加える。
- **FR-008**: 返済表の各回の支払額の合計は、支払総額と一致しなければならない。
- **FR-009**: 返済表の各回の元金の合計は、利用金額と一致しなければならない。
- **FR-010**: 返済表の最終回の支払後の残高は、0円でなければならない。
- **FR-011**: 金額の計算は、途中で誤差の出ない方法で行い、丸めは FR-006・FR-007 に書いた箇所でだけ
  行わなければならない（constitution 原則III）。

**出力**

- **FR-012**: システムは、毎月の支払額・手数料の合計・支払総額を表示しなければならない。
  初回の支払額が2回目以降と異なる場合は、初回と2回目以降の額を分けて表示する。
- **FR-013**: システムは、返済表（回・支払額・手数料・元金・支払後の残高）を、1回目から最終回まで表示しなければならない。
- **FR-014**: 金額は円単位で、3桁ごとに区切って表示しなければならない。

**画面の入力欄の表示（Should）**

2026-11-20 に、画面の動作確認での要望を受けて追加した。以下は、満たすことが望ましい（Should）要件とする。

- **FR-015**: 利用金額の入力欄は、フォーカスが外れたときに、入力された値を3桁区切りのカンマを付けて表示するとよい
  （例：`100000` → `100,000`）。API に送るときは、カンマを取り除いて送る。
  利用者が自分でカンマを入れた値（例：`100,000`）も、同じくカンマを取り除いて送り、受け付ける。
  カンマを取り除いても半角数字だけにならない値（例：`abc`・`1000.5`）は整えず、入力されたまま残す
  （API の入力チェックで、形式の誤りになる）。
- **FR-016**: 実質年率の入力欄は、整数が入力されたとき、フォーカスが外れたときに小数第1位まで表示するとよい
  （例：`15` → `15.0`）。整数でない値（例：`abc`・`12.25`）は整えず、入力されたまま残す。
- **FR-017**: FR-015・FR-016 で値を整えるのは画面の中だけとし、API の入力のルール（カンマ付きの利用金額は形式の誤り。
  [contracts](contracts/installment-simulation-api.md)）は変えない。
- **FR-018**: 入力中（フォーカスがある間）は、カンマを差し込まない（カーソルの位置がずれるため）。

**画面のデザイン（Should）**

2026-11-20 に追加した。以下は、満たすことが望ましい（Should）要件とする。

- **FR-019**: 画面は、明るい緑で親しみやすい配色にするとよい。
  色の組み合わせ・ロゴ・レイアウトは独自のもので、実在の会社のデザインに似せない。
  - 注記（2026-11-24）：ユーザーの判断で変えた。変える前は「緑を基調とした、落ち着いた金融サービスらしい配色」。
    実装のときの指示（明るい緑で、親しみやすい感じ）に合わせた。
- **FR-020**: 返済表と要約の金額の列は右寄せにして、桁をそろえるとよい。
- **FR-021**: 文字と背景の色の差（コントラスト）を十分に取り、読みやすさを保つとよい。
  基準は WCAG 2.1 AA とする（通常の文字で 4.5:1 以上）。
- **FR-022**: 入力エラーの赤字は、緑を基調とした画面の中でも目立つようにするとよい。
  - 注記（2026-11-24）：ユーザーの判断で直した。直す前は「緑の背景の中でも」。
    エラーは緑の上に直接ではなく、白いカードの上にうすい赤の背景を付けて出すので、それに合わせた。赤字が目立つようにする意図は変えない。

### Key Entities

- **シミュレーション条件**：利用金額・支払回数・実質年率。
- **シミュレーション結果**：毎月の支払額・手数料の合計・支払総額・返済表。
- **返済表の行**：回（1〜支払回数）・支払額・手数料・元金・支払後の残高。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 利用者は、画面を開いてから30秒以内に、シミュレーション結果を確かめられる。
- **SC-002**: あらかじめ用意した検証用の条件（端数が出る条件・年率0%・上限と下限を含む）のすべてで、
  結果が手計算の期待値と1円単位で一致する。
- **SC-003**: すべての結果で、支払額の合計＝支払総額、元金の合計＝利用金額、最終回の残高＝0円 が成り立つ。
- **SC-004**: 未入力・範囲外・形式の誤った入力は100%入力エラーになり、誤った計算結果が表示されることはない。
- **SC-005**: 入力してから結果が表示されるまで、1秒以内である。

## Assumptions

- 範囲外：認証・ログイン、実際の決済、本物のカード番号の扱い、ボーナス払い、リボ払い
  （リボ払いは別の機能として仕様を作る）。
- MVPの範囲に挙がっていないため、繰上げ返済・支払回数の途中変更・支払回数ごとの比較表・
  結果の保存も範囲外とする（constitution 原則VIII）。
- この機能では、カード番号や個人情報を入力・保存しない。
- 100円あたりの手数料の表を使う方式は扱わない。
- 支払回は「1回目・2回目…」で表し、具体的な支払日（年月日）や日割りの計算は扱わない。
- 利用金額の範囲（1,000円〜10,000,000円）は、シミュレーターとして十分な範囲として仮に決めた。
