# 機能仕様：カードの申込管理

**Feature Branch**: `docs/card-application-spec`

**Created**: 2026-11-17

**Status**: Draft

**Input**: User description: "クレジットカードの申込管理機能。カード会社の担当者が、カードの申込を登録し、審査の進み具合を管理できるようにする。"

## 優先度の表し方

- **Must**：MVPに必ず含める。
- **Should**：MVPに含めるが、Mustがすべて終わってから着手し、遅れたときは削ってよいもの。
- 要件に何も書いていないものは、Mustとする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 申込を登録する (Priority: P1)

カード会社の担当者が、申込者の氏名・生年月日・年収・勤務先名などを入力して、カードの申込を登録できる。
登録した申込は保存され、状態は「申込」になる。

**Why this priority**: 申込がなければ、一覧も審査の管理もできない。この機能のすべての出発点。

**Independent Test**: 正しい内容で申込を登録し、申込番号が割り当てられ、状態が「申込」で保存されること、
画面を開き直しても同じ内容を確かめられることで確かめられる。

**Acceptance Scenarios**:

1. **Given** 6項目すべてに正しいダミー情報を入力した状態, **When** 申込を登録する,
   **Then** 申込が保存され、申込番号が割り当てられ、状態は「申込」になる
2. **Given** 申込を登録した状態, **When** 画面を開き直す（またはシステムを再起動する）,
   **Then** 登録した申込の内容と状態がそのまま残っている
3. **Given** 未入力・範囲外・形式の誤りがある項目を含めて入力した状態, **When** 申込を登録する,
   **Then** 申込は保存されず、誤っているすべての項目に、直し方が分かるメッセージが表示される

---

### User Story 2 - 申込の一覧と詳細を見る (Priority: P2)

担当者が、登録されている申込を一覧で確かめ、状態で絞り込み、1件を選んで詳細（入力した全項目・状態・
申込日時・更新日時・状態の変更履歴）を見られる。

**Why this priority**: どの申込がどこまで進んでいるかを把握するために必要。登録（P1）があって意味を持つ。

**Independent Test**: 状態の違う申込を何件か登録し、一覧に新しい順で表示されること、状態で絞り込めること、
1件を選ぶと、登録した内容と一致する詳細が表示されることで確かめられる。

**Acceptance Scenarios**:

1. **Given** 申込が3件登録されている状態, **When** 一覧を開く,
   **Then** 3件が申込日時の新しい順に表示され、各行に申込番号・氏名（漢字）・状態・申込日時がある
2. **Given** 状態が「申込」2件・「審査中」1件・「承認」1件の状態, **When** 状態「申込」で絞り込む,
   **Then** 「申込」の2件だけが、申込日時の新しい順に表示される
3. **Given** 状態で絞り込んだ状態, **When** 絞り込みを「すべて」に戻す, **Then** すべての申込が表示される
4. **Given** 状態が「否決」の申込が1件もない状態, **When** 状態「否決」で絞り込む,
   **Then** 該当する申込がないことが分かるメッセージが表示される
5. **Given** 一覧を表示した状態, **When** 1件を選ぶ,
   **Then** その申込の全項目・状態・申込日時・更新日時・状態の変更履歴が表示される
6. **Given** 申込が1件もない状態, **When** 一覧を開く, **Then** 申込がないことが分かるメッセージが表示される
7. **Given** 存在しない申込番号の詳細を開こうとした状態, **When** 詳細を表示する,
   **Then** 申込が見つからないことが分かるメッセージが表示される

---

### User Story 3 - 審査の状態を進める (Priority: P3)

担当者が、申込の状態を「申込 → 審査中 → 承認／否決」の順に変更し、審査の進み具合を管理できる。
状態を変えるときは担当者名を入力し、否決するときは理由も入力する。変更の経過（誰がいつ変えたか）は、あとから詳細で追える。

**Why this priority**: 審査の進み具合を管理するという目的に必要。ただし、登録と一覧（P1・P2）だけでも申込の把握はできる。

**Independent Test**: 1件の申込の状態を「申込」→「審査中」→「否決」と変更し、
各変更が保存されて一覧と詳細（変更履歴を含む）に反映されること、許されない変更、担当者名のない変更、
理由のない否決はエラーになることで確かめられる。

**Acceptance Scenarios**:

1. **Given** 状態が「申込」の申込, **When** 担当者名「テスト 担当A」を入力して状態を「審査中」に変更する,
   **Then** 状態は「審査中」になり、更新日時が変わり、変更履歴に「申込→審査中」・変更日時・担当者名「テスト 担当A」の1行が加わる
2. **Given** 状態が「審査中」の申込, **When** 担当者名を入力して状態を「承認」に変更する,
   **Then** 状態は「承認」になり、変更履歴に「審査中→承認」と入力した担当者名が加わる
3. **Given** 状態が「審査中」の申込, **When** 担当者名と理由を入力して状態を「否決」に変更する,
   **Then** 状態は「否決」になり、変更履歴に「審査中→否決」と入力した担当者名・理由が加わる
4. **Given** 状態が「審査中」の申込, **When** 担当者名は入力し、理由を入力せずに（または空白だけで）状態を「否決」に変更しようとする,
   **Then** 変更は行われず、否決の理由を入力するよう求めるメッセージが表示される
5. **Given** 状態が「申込」の申込, **When** 担当者名を入力せずに（または空白だけで）状態を「審査中」に変更しようとする,
   **Then** 変更は行われず、担当者名を入力するよう求めるメッセージが表示される
6. **Given** 状態が「申込」の申込, **When** 状態を「承認」または「否決」に直接変更しようとする,
   **Then** 変更は行われず、先に「審査中」にする必要があることが分かるメッセージが表示される
7. **Given** 状態が「承認」または「否決」の申込, **When** 状態をほかの値に変更しようとする,
   **Then** 変更は行われず、審査が終わった申込の状態は変えられないことが分かるメッセージが表示される
8. **Given** 「申込→審査中→承認」と変更した申込, **When** 詳細を開く,
   **Then** 変更履歴に2行が、変更日時の古い順に表示される

---

### User Story 4 - キーワードで探し、ページを分けて見る (Priority: P4・Should)

申込が増えたとき、担当者が氏名や申込番号のキーワードで申込を探し、一覧をページに分けて見られる。

**Why this priority**: 申込が多いと探しやすくなるが、状態の絞り込み（P2）があれば、MVPの件数では把握できる。
遅れたときは削ってよい（Should）。

**Independent Test**: 申込を25件登録し、キーワードで該当する申込だけが表示されること、
一覧が20件ずつのページに分かれることで確かめられる。

**Acceptance Scenarios**:

1. **Given** 氏名（カナ）が「テスト　タロウ」（姓と名の間は全角スペース）の申込がある状態, **When** キーワード「タロウ」で検索する,
   **Then** 氏名（漢字）・氏名（カナ）・申込番号のどれかに「タロウ」を含む申込だけが表示される
   （2026-11-25 にユーザーの判断で直した：例の姓と名の間が半角スペースで、FR-002 と合わなかったため。FR-002 を正とした。plan の research.md R9）
2. **Given** キーワードで検索した状態, **When** あわせて状態で絞り込む, **Then** 両方の条件に合う申込だけが表示される
3. **Given** 申込が25件ある状態, **When** 一覧を開く, **Then** 1ページ目に新しい順の20件が、2ページ目に残りの5件が表示される
4. **Given** 該当する申込がないキーワード, **When** 検索する, **Then** 該当する申込がないことが分かるメッセージが表示される

---

### Edge Cases

- 生年月日がちょうど18歳になる日のとき：登録できる。18歳になる日の前日（17歳）のとき：入力エラーになる
- 生年月日がちょうど100歳になる日のとき、および100歳のあいだ（101歳になる日の前日まで）：登録できる。
  ちょうど101歳になる日のとき：入力エラーになる（年齢は満年齢。FR-002 の「100歳以下」）
  （2026-11-25 にユーザーの判断で直した：もとは「ちょうど18歳・100歳になる日：登録できる。1日でも外れるとき：入力エラー」で、
  100歳の側が FR-002 の「100歳以下」（満年齢）と合わなかったため。FR-002 を正とした。plan の research.md R10）
- 生年月日が未来の日付、または存在しない日付（例：2月30日）のとき：入力エラーになる
- 年収が0万円・9,999万円のとき：登録できる。1万円でも外れるとき：入力エラーになる
- 年収に小数・負の数・数字以外の文字が入力されたとき：入力エラーになる
- 文字数の上限ちょうどの氏名・勤務先名・担当者名・否決の理由：登録できる。1文字超えるとき：入力エラーになる
- 氏名・勤務先名・担当者名・否決の理由が空白だけのとき：未入力として扱う。前後の空白は取り除いて保存する
- 実際には別の人が、ほかの担当者の名前を入力したとき：システムは見分けられず、入力された名前のまま履歴に残る（FR-016）
- 電話番号が9桁・12桁、0以外で始まる、ハイフンを含むとき：入力エラーになる
- 同じ内容の申込を2回登録したとき：別々の申込として、それぞれに申込番号が割り当てられる
- 2人の担当者が同じ申込の状態を同時に変更したとき：あとから変更した側は、状態がすでに変わっていることを示すエラーになり、
  上書きされない
- 状態で絞り込んだあとに、ほかの担当者が状態を変えたとき：一覧を開き直すと、新しい状態で絞り込まれる
- 入力項目にカード番号を入れる欄はない（カード番号は扱わない）

## Requirements *(mandatory)*

### Functional Requirements

**登録**

- **FR-001**: 担当者は、氏名（漢字）・氏名（カナ）・生年月日・年収・勤務先名・電話番号の6項目を入力して、
  申込を登録できなければならない。6項目とも必須とする。
- **FR-002**: 各項目は、次の条件を満たさなければならない。

  | 項目 | 条件 |
  |------|------|
  | 氏名（漢字） | 1文字以上50文字以下 |
  | 氏名（カナ） | 全角カタカナと全角スペースだけで、1文字以上50文字以下 |
  | 生年月日 | 実在する日付で、申込日時点で18歳以上100歳以下 |
  | 年収 | 万円単位の整数で、0万円以上9,999万円以下 |
  | 勤務先名 | 1文字以上100文字以下 |
  | 電話番号 | 数字だけ（ハイフンなし）で、0から始まる10桁または11桁 |

- **FR-003**: 入力が FR-001・FR-002 を満たさないとき、システムは申込を保存せず、誤っているすべての項目に、
  直し方が分かるメッセージを表示しなければならない。
- **FR-004**: 申込を登録したとき、システムは重ならない申込番号を割り当て、状態を「申込」とし、
  申込日時（登録した日時）と更新日時を記録しなければならない。
- **FR-005**: 申込のデータは、システムを再起動しても消えないように保存しなければならない。
- **FR-006**: 登録した申込の内容（氏名・生年月日など）は、あとから変更できない。申込の削除もできない。

**一覧と詳細**

- **FR-007**: システムは、申込の一覧を、申込日時の新しい順に表示しなければならない。
  各行には、申込番号・氏名（漢字）・状態・申込日時を表示する。
- **FR-008**: 担当者は、一覧を状態（すべて・申込・審査中・承認・否決のどれか1つ）で絞り込めなければならない。
  最初は「すべて」とする。絞り込んでも、並び順は申込日時の新しい順とする。
- **FR-009**: 一覧に表示する申込がないとき、システムは該当する申込がないことが分かるメッセージを表示しなければならない。
- **FR-010**: 担当者が一覧から1件を選ぶと、システムはその申込の全項目・状態・申込日時・更新日時・
  状態の変更履歴（FR-018）を表示しなければならない。
- **FR-011**: 年収は「万円」を付け、3桁ごとに区切って表示しなければならない。日時は日本時間で表示する。
- **FR-012**（Should）: 担当者は、キーワードで申込を検索できる。氏名（漢字）・氏名（カナ）・申込番号のどれかに
  キーワードを含む申込を表示する（部分一致）。状態の絞り込みと組み合わせられる。
- **FR-013**（Should）: 一覧は、1ページ20件ずつに分けて表示する。

**状態の変更**

- **FR-014**: 申込の状態は、「申込」「審査中」「承認」「否決」の4つとする。
- **FR-015**: 許される状態の変更は、「申込→審査中」「審査中→承認」「審査中→否決」の3つだけとする。
  承認と否決は最終の状態で、ほかの状態に戻せない。それ以外の変更（例：「申込→承認」「承認→審査中」）は行わず、
  許されない変更であることが分かるメッセージを表示しなければならない。
- **FR-016**: 状態を変更するときは、担当者名（1文字以上50文字以下、空白だけは未入力として扱う）の入力を
  必須としなければならない。担当者名がないとき、変更は行わない。
  認証がないため、担当者名は自己申告であり、システムは本人確認をしない（入力された名前が本当にその人かは確かめない）。
- **FR-017**: 状態を「否決」に変更するときは、担当者名に加えて、否決の理由（1文字以上500文字以下、
  空白だけは未入力として扱う）の入力を必須としなければならない。理由がないとき、変更は行わない。
- **FR-018**: 状態を変更したとき、システムは更新日時を記録し、変更履歴に1行（変更日時・変更前の状態・変更後の状態・
  担当者名、否決のときは理由）を加えなければならない。変更履歴は、詳細の画面に変更日時の古い順で表示する。
- **FR-019**: 状態を変更しようとしたとき、すでにほかの担当者が状態を変えていた場合は、変更を行わず、
  最新の状態を確かめるよう促すメッセージを表示しなければならない。

**個人情報とカード情報**

- **FR-020**: 登録画面には、ダミーの情報だけを入力するよう注意書きを表示しなければならない（constitution 原則IV）。
- **FR-021**: この機能では、カード番号を入力・保存・表示しない。承認しても、カード番号は発行しない。
- **FR-022**: 見本やテストに使う申込のデータは、明らかに架空と分かるものだけを使わなければならない（constitution 原則IV）。

### Key Entities

- **申込**：申込番号・FR-001 の6項目・状態・申込日時・更新日時。登録後に内容は変わらず、状態と更新日時だけが変わる。
- **状態**：申込・審査中・承認・否決のいずれか。許される変更は FR-015 に従う。
- **状態の変更履歴**：申込番号・変更日時・変更前の状態・変更後の状態・担当者名（自己申告）・否決の理由（否決のときだけ）。
  1件の申込に、0行以上（最大2行）がつく。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 担当者は、画面を開いてから2分以内に、1件の申込を登録できる。
- **SC-002**: 担当者は、一覧を状態で絞り込み、目的の申込の詳細を10秒以内に確かめられる。
- **SC-003**: 未入力・範囲外・形式の誤りのある入力は100%登録されず、誤った申込が保存されることはない。
- **SC-004**: FR-015 で許されていない状態の変更、担当者名のない変更、理由のない否決は100%行われない。
- **SC-005**: 登録した申込、状態の変更、変更履歴は、システムを再起動しても100%残っている。
- **SC-006**: 申込が100件あっても、一覧（絞り込みを含む）は1秒以内に表示される。

## Assumptions

- 範囲外：認証・ログイン（担当者を区別しない）、自動の審査ロジック、信用情報機関などとの外部連携、メール通知、申込の削除。
- MVPの範囲に挙がっていないため、申込内容の変更、一覧の並べ替え（申込日時の新しい順以外）、CSVなどへの出力、
  カード番号の発行も範囲外とする（constitution 原則VIII）。
- キーワード検索とページ分けは範囲外ではなく、Should とする（FR-012・FR-013）。
- 使う人は、カード会社の担当者だけとする。申込者本人がこの画面を使うことはない。
- 申込番号の形式（例：「A」＋連番）は、計画（plan）で決める。担当者が入力することはない。
- 年齢は、申込日（日本時間）と生年月日から、満年齢で計算する。18歳は成年年齢に合わせた。
- 年収の単位（万円）と上限（9,999万円）は、審査の目安として十分な範囲として決めた。
- 否決の理由の上限（500文字）は、理由を書くのに十分な長さとして仮に決めた。
- 状態は申込ごとに1つで、同時に2つの状態になることはない。
- 担当者名は、状態を変えるたびに入力する自己申告の値で、本人確認はしない（認証が範囲外のため）。
  担当者の一覧や登録は持たず、入力された名前をそのまま履歴に残す。
- 担当者名も個人情報になりうるため、見本やテストでは架空の名前（例：「テスト 担当A」）を使う（constitution 原則IV）。
