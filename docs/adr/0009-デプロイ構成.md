# 0009 デプロイ構成：EC2上のdocker compose、GHCR、OIDC＋SSM

## 状態

Accepted（2026-11-17）

## 背景

- 11/27の説明で、EC2上のデモを見せる必要がある（Day1で判明。`docs/sprint-plan.md`「実績」）。
- 前回の課題のAWSアカウントを使う。
- 申込管理では、データを再起動しても消えないように保存する必要がある（`specs/003-card-application/spec.md` FR-005）。
- リポジトリはPublicなので、秘密情報をコミットしてはならない（constitution 原則VII）。

## 決定

- AWS EC2の上で、docker composeでアプリ（jar）とPostgreSQL（[0011](0011-DB.md)）を動かす。
- GitHub Actionsでイメージを作り、GHCR（GitHub Container Registry）に保存する。
- GitHub ActionsからAWSへはOIDCで認証し、SSM（Systems Manager）でEC2に反映する。
- mainにマージすると、EC2に自動でデプロイされる（Day4）。

選んだ理由：

- SSHのポートを開けずに済む。
- AWSの鍵（アクセスキー）をGitHubに保存せずに済む。
- RDSと比べて、費用と手間が少ない。MVPでは、DBは1台で十分である。

## 検討した他の案

| 案 | 採らなかった理由 |
|---|---|
| DBをRDSに置く | EC2とは別に月額の費用がかかる。ネットワークやセキュリティグループの設定の手間も増える。MVPでは、DBは1台で十分である。 |
| SSHでEC2に入ってデプロイする | SSHのポートを開ける必要があり、SSHの鍵やAWSの鍵をGitHubに保存することになる。 |

## 結果

### 良い影響

- 外から入れる口（SSH）を開けずにデプロイできる。
- 長く使える秘密情報（AWSの鍵）をGitHubに置かない。
- アプリとDBを1つのcomposeで、開発環境と同じ形で動かせる。

### 悪い影響

- DBがEC2の上にあるので、EC2の障害・停止・削除でデータに影響する。バックアップは自分で用意する必要がある。
- 使わない時間はEC2を停止する運用なので、その間はデモ環境が使えない（`docs/sprint-plan.md`「毎日の決まりごと」）。
- OIDC・IAM・SSMの設定が要る。権限が要る操作なので人が行う（constitution「開発ワークフローと人とAIの分担」）。
- 将来RDSに移すときは、DBの移行が要る（[0011](0011-DB.md)）。
