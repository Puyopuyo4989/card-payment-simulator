# 0006 カバレッジ基準

## 状態

Accepted（2026-11-18）

## 背景

- constitution 原則II：行カバレッジと分岐カバレッジは、どちらも90%以上とする。バックエンド・フロントエンドのそれぞれに適用する。
- 90%未満を認めるのは、テストが1,000件以上あり、かつ理由をADRに記録した場合だけとする。
- 計測から除外してよい対象はADRで定める。ADRにない対象を除外してはならない。
- 品質基準を数値で示し、ビルドとCIで自動的に確かめられるようにするため（constitution 原則II の理由）。

## 決定

- 行カバレッジ・分岐カバレッジとも90%以上。バックエンドとフロントエンドのそれぞれで満たす。
- 例外の条件「テスト1,000件以上」の1,000件は、**バックエンドとフロントエンドの合計件数**とする。
- 例外を使うときは、理由をADRに記録する。
- 計測ツール：
  - バックエンド：JaCoCo（`jacoco-maven-plugin`）。Java 25 に対応した版（0.8.14 以降。今は 0.8.16）に固定する。
  - フロントエンド：Vitest の `@vitest/coverage-v8`。
- 計測から除外してよい対象は、次だけとする。
  - `CardPaymentSimulatorApplication`（起動クラス）
  - `frontend/vite.config.ts`
  - `frontend/src/setupTests.ts`
  - テストのファイル（`src/test/` の下、`frontend/src/**/*.test.ts(x)`）
- フロントエンドは `frontend/src/` の下だけを計測する（`include`）。そのため、`src/` の外（`vite.config.ts` など）は計測の範囲外になる。
- 次は除外しない。除外は最小限にして、都合のよい除外を防ぐ。
  - record・DTO
  - `types.ts`
  - `frontend/src/main.tsx`
- `./mvnw verify` で、バックエンド・フロントエンドのどちらかが、行・分岐のどちらかで90%未満なら、ビルドを失敗させる。

## 検討した他の案

| 案 | 採らなかった理由 |
|---|---|
| record・DTO・`types.ts`・`main.tsx` も除外する | 除外を広げると、テストのない処理を見落とし、都合よくカバレッジを上げられる。除外は最小限にする。 |
| バックエンドで JaCoCo 以外のツールを使う | JaCoCo は、Maven と Java で最も広く使われている計測ツールで、CI や PR のレポートとの連携の情報も多い。他のツールを採る理由がない。 |
| フロントエンドで `@vitest/coverage-istanbul` を使う | `@vitest/coverage-v8` は Vitest の標準の計測方法で、コードを書き換えずに JavaScript エンジンの機能で計測するため速い。istanbul はコードの書き換えが要り、遅くなる。 |

## 結果

### 良い影響

- ビルドとCIで、基準を満たしているかを自動で確かめられる（`./mvnw verify` で閾値を確かめる）。
- 除外対象をADRで限定するので、都合よく除外してカバレッジを上げることを防げる。

### 悪い影響

- 90%を満たすためのテストを書く時間が要る。
